# 演示与验收指南

推荐在独立浏览器或无真实数据的测试窗口操作。数据只存在当前浏览器中；「载入完整演示」和重置会改写该版本的本机记录。若已有填写内容，请先在确认记录中导出项目。

## 快速看三版

在 `mingma-lab` 运行 `npm ci`、`npm run dev`，打开 [设计展厅](http://127.0.0.1:5188/)。依次进入雾屿、澄境与筑序，比较首页、需求清单和方案比对。三版均可操作，并非静态设计稿。

展厅提供桌面与手机截图、8 项验收清单。清单按版本分别保存；完成一版不会将其他版标为已验收。

## 完整演示路径

| 步骤 | 操作 | 应看到的结果 |
| --- | --- | --- |
| 1. 表达需求 | 进入需求共创，输入「厨房想好打理，预留洗碗机，保留现有布局和窗，不要开放展示格」 | 原始表达被保留，随后进入问题澄清 |
| 2. 回答问题 | 选择保留现有布局；洗碗机、电饭煲、咖啡机；容易擦拭、减少接缝；不要开放展示格；保留现有窗 | 生成 6 条厨房需求，尺寸、接口等仍列为待确认 |
| 3. 发布基准 | 查看需求描述与优先级，确认并发布 | 产生 R1；只有主动发布才成为方案核对基准 |
| 4. 比较商家 | 在方案比对载入演示商家 | 木序设计的洗碗机供排水说明不足；栖居营造的开放展示格与用户需求冲突 |
| 5. 查看依据 | 点击对应项目的原文依据 | 展示方案原文、缺口与下一步，不只是一个判断标签 |
| 6. 反馈修订 | 生成反馈，进入商家工作区；选对应商家，修改说明或填入修订示例，再提交 | 形成新的方案版本；重新检查已补充的文字说明，现场未知项继续保留 |
| 7. 用户选择 | 阅读当前方案与待办后选定 | 确认记录保存需求版本、方案版本及未决事项 |
| 8. 检查变更 | 修改需求并发布 R2，再返回方案比对 | 旧方案提示需按新基准核对，历史选择仍保留其 R1 快照 |

也可用首页完整演示快捷入口直接观察已有 R1 和商家回应，但答辩时建议至少手动演示一次「反馈 → 修订 → 重新核对」。

## 辅助功能验收

**维度量表：** 检查业主 10 项、商家 9 项。未填依据时尝试选择 3 级，应被阻止；填写确认依据后可以设为 3 级。移除依据时不能继续保持「已确认」。优先级与成熟度分别记录，刷新可恢复。

**空间预览：** 切换房间、拖动或使用键盘旋转、切换俯视、开关墙体和线路图层。对没有空间资料的商家，应看到资料缺口，不应显示属于独立演示户型的路线。

**单商家与草稿：** 只提交一家商家时，另一家保持未提交，不出现无效原文链接。切换商家或页面后，未提交草稿应能够恢复。

**版本隔离：** 一家商家针对 R2 提交新方案，另一家仍引用 R1；当前版本方案的选择资格应独立判断，旧版本方案仍保留待核对提示。

**三版特色：** 雾屿首页生活便签可进入需求澄清，且不覆盖已发布需求；澄境首页区域需求可打开对应说明；筑序可通过章节导航进入各功能页并查看侧边证据批注。

**响应式：** 检查 390px 手机宽度和桌面宽度。页面不应产生整体横向溢出，主按钮、导航、弹窗和表单需可操作；内部对照表或章节导航可按设计横向滚动。

## 向评委说明的边界

可以这样介绍当前成果：

> 我们先把用户需求固定成可追溯的基准，再让商家逐项回应，检查说明是否缺失或冲突。当前演示使用可解释的本地规则；自定义需求、现场条件和超出规则范围的内容保留人工确认。用户的最终决定会同时留下需求版本、方案版本和未决事项。

不要把规则核对描述为已经接入的大模型能力，不把「已回应」描述为施工验收通过，不把示例模型描述为真实施工图。自动学习与经验库在产品规划中，当前没有自行训练或更新规则的服务。

```sh
cd mingma-lab

npm run build
npm run preview -- --port 5190
```

在 [生产预览](http://127.0.0.1:5190/) 重复关键流程，可检查打包后的实际行为。历史自动与人工检查范围见 [`verification.json`](../mingma-lab/review/verification.json)。当前 GitHub Actions 运行领域测试和构建，不自动覆盖本文全部浏览器与视觉验收。
